# v16：修复 RGB 连续扫描的 EOF 补块失步

ESP32-S31 的 PSRAM 行号图出现重复、移动时，LCD 帧结束频率仍约 35.4Hz，但每帧只处理约 16 个 DMA EOF，补充 480 行本应需要 48 个。v16 将 `AXI_DMA OUT_CONF0.OUT_EOF_MODE` 显式设为 0，使通知对应数据读入 DMA FIFO 的时刻。用户运行只改变这一项的诊断版后，反馈画面看起来已修复；本版将相同配置用于完整 Slint 风扇控制界面。

## 原因与责任范围

链路为：PSRAM 帧缓冲 → CPU 拷贝 → 内部 RAM 的 4×10 行缓冲 → AXI DMA FIFO → LCD_CAM。

每块末尾的 EOF 表示该块传输进度，不是 LCD 的整帧结束。软件依靠它逐块补充下一批源行。锁定的 esp-hal `bb239a0f4adc45b2571586c3ea55f56ecc712e00` 没有设置这项策略，应用也沿用了复位值 1，即 FIFO 输出端通知。此配置在已测 S31 链路上出现固定 3:1 的 EOF 节拍异常：每次报告的块号向前跨三块，ISR 只补最新完成的一块，另外两块随后重放旧数据。

固定 SRAM 彩条不需要补块，所以相同异常可以不影响它的稳定性。PSRAM 行号图每块内容不同，旧块便表现为重复或位移。DMA 仍能读到有效内存，因此 `DMA错误=0`、`欠载=0` 并不意味着内容正确。

这是当前驱动对 S31 的 EOF 策略配置不完整，现有证据支持继续使用 Rust / esp-hal、Slint 和 bounce buffer 架构。官方 RGB 驱动同样显式设置 `eof_till_data_popped=false`，本修复通过 Rust PAC 写寄存器实现，无须引入 IDF 应用运行时。为什么该芯片组合在模式 1 下恰好呈现三分之一的通知频率，尚无硬件级证据可进一步归为芯片勘误或中断交付缺陷。

## 正式版内容

- 默认启用 FIFO 输入端 EOF 通知，在 DMA 时钟已开启、传输尚未开始时配置。启动后读回 `eof_popped=false`。
- 运行完整 Slint 界面、GT1151 触摸及 RMT 风扇控制；保留 18MHz PCLK、4×10 行内部 RAM 环、PSRAM 双帧缓冲与发布握手。
- 保留现有主循环统计；移除本轮临时 `[DIAG]` 插桩、测试入口和试验 feature。
- 修正 PCLK “已确认根因”的旧注释：基线请求 ShiftHigh，但实际读回 edge=false，尚未证明它造成此次故障。本次经验证的行为变更仅是 EOF 策略。
- 构建脚本锁定 Cargo.lock，明确构建 `fan-control-fw`，并校验镜像完整性及分区边界。

完整 Slint 界面的硬件运行验证与诊断页验证是两步。本正式包完成编译和镜像校验，完整界面的画面稳定性、触摸换档和持续负载仍需烧录后验收。应观察 EOF/VSYNC 接近 48、约 1699 EOF/s，且失步计数不持续增长。

## 实现参考

- esp-hal：`esp-hal/src/dma/engine/axi_gdma.rs`，锁定版本见本包 `BUILD.json`。
- ESP-IDF RGB 驱动：`components/esp_lcd/rgb/esp_lcd_panel_rgb.c` 中 `lcd_rgb_create_dma_channel()` 的 EOF 策略。
- ESP-IDF `gdma_strategy_config_t.eof_till_data_popped`：false 为 DMA FIFO 输入端通知，true 为输出端通知。

IDF 参考代码为排查时读取的在线 master，用于核对寄存器语义；不能据此声称朋友所安装的精确版本完全相同。
